# 最少代码梯子（lazy-ladder）

iloop 在 [I]/[P]/[E]/[R]审查 使用的实现约束。
提炼自 [ponytail](https://github.com/DietrichGebert/ponytail)（MIT）：只取 7 级梯子与「不许偷懒」清单，不引入档位、hooks、`/ponytail` 命令。

先读懂问题与触及的代码，再爬梯子。懒的是方案，不是阅读。

## 冲突优先级（高 → 低）

1. T0（角色写权限、禁止计划外功能、开发不写 `test/`）
2. 冻结的验收标准（WHAT）
3. 本梯子（HOW）
4. 计划里的建议文件 / 逻辑说明

验收被写成实现形态（例如「必须新建 `Foo.tsx`」）时仍冻结。开发不得擅自改道，须回退 PM，归类为计划缺陷。

## 7 级梯子

停在第一级还能站住的方案上：

1. **这件事需要存在吗？（YAGNI）** 投机需求就跳过。执行阶段本级只禁止加料，不砍本步需求；开发认为某步不该存在 → 中断回退 PM，不得自己跳过。
2. **仓库里已经有了吗？** 复用现有 helper / 类型 / 模式，不重写。
3. **标准库能做吗？** 用标准库。
4. **平台原生能力能做吗？** 用原生（如 `<input type="date">`、CSS、数据库约束）。
5. **已装依赖能做吗？** 用已装依赖。不为几行代码新加包。
6. **能一行吗？** 一行。
7. **以上都不行：** 才写能跑的最少代码。

两级都能站住 → 取更高一级（编号更小）并继续。修 bug 修根因：改共享函数一次，不给每个 caller 打补丁。

## 铁律

- 不写没人要的抽象、工厂、永远不变的配置项。
- 不写「以后再用」的样板。
- 删优于加。无聊优于聪明。文件越少越好。
- 两个同等篇幅的标准库方案，选边例正确的那个。
- 故意切角且有已知上限时，用一行注释标明上限与升级路径（`# lazy-ladder: global lock, per-account locks if throughput matters`）。

## 不许偷懒

理解问题（先读再爬梯子）、信任边界校验、防丢数据的错误处理、安全、无障碍、硬件校准、用户明确要求的东西。

开发不在 `test/` 写验收脚本（QA 职责）。只跑仓库既有测试自查。

## 改道评论格式

因更高 rung 改道且验收仍能过时，Issue 评论一行：

`步骤 N: skipped: <未写之物>, used: <实际采用>, add when: <何时才需要被跳过的方案>`

例：`步骤 3: skipped: 新建 DatePicker.tsx, used: <input type="date">, add when: 需要自定义日历皮肤`
