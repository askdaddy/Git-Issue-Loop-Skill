# 运行时反馈闭环

本协议服务于 iloop 维护改进，不替代业务 Issue 的验收。反馈不是处罚计数。

## 检测与止损

| 场景 | 规则 | 来源 | 下一步 |
|---|---|---|---|
| 已知角色被拒绝操作 | ROLE-001 | check_permission 固定诊断 | 保留原拒绝，核对角色和动作 |
| 工作区路径或 Issue 分支越界 | WORKSPACE-001 | guard 固定诊断 | 停止提交，核对变更归属 |
| 标签超前、缺优先级或缺阶段证据 | ISSUE-001 | 分发/交接人工结构检查 | 按现有状态权限补齐或回退 |

每次阶段交接检查优先级、唯一状态、阶段产物、未完成验收及已记录偏差。
只检测结构，不声称能自动判断内容质量、计划语义或发现所有绕过。
无角色时保留人工兼容放行，`scope=unattributed` 只表示无法归因，不表示已违规。
共享工作区的 guard 异常先记疑似，不据路径直接归责。已发生越界先停止相关动作并保留证据，不能自动删除他人变更。

## 草稿与事实

在对话中执行 `bash <Skill根>/scripts/feedback.sh draft <场景> <分类>`：
场景为 `permission|guard|evidence`；分类为 `suspected|confirmed|intercepted|false-positive`。
默认推荐 suspected；confirmed 需要复核证据；intercepted 表示成功拦截而非已造成损害；false-positive 必须关联原事件并说明更正依据。
命令仅输出草稿、不提交、不写文件；允许全部角色调用。证据场景由 Agent 调用，不是自动审计。

草稿的 unknown 必须由 Agent 在对话中人工核对补充：角色、阶段、预期/实际、检测来源、最小脱敏证据、影响、处置、归因、关联任务/事件。未知仍保留 unknown。
归因可为 Agent 未遵守、脚本缺口、规范冲突、历史内容缺失、环境、待确认；拒绝一次不等于 Skill 有缺陷。
规则码是稳定标识；粗粒度指纹是规则+症状，人工核对是否同根因，不能仅凭指纹合并。
事件 ID 区分发生实例；时间加进程号仅供本机草稿参考，提交前核对唯一性，跨机冲突时加人工实例后缀。

原业务 Issue 评论记录事件、事实与处置，普通格式/证据补齐不计产品 QA retry；产品验收 FAIL 仍走原流程。
遵守角色权限，不能因反馈需求越权改状态或文件。反馈功能失败不能覆盖原始错误、退出码或拒绝结果；诊断不调用草稿生成器。

## 脱敏、去重与授权

默认白名单只有固定规则/症状、枚举分类、UTC 参考 ID、Skill tag/SHA；其他业务信息由用户审阅后补充。
禁止自动粘贴原始命令参数、日志、环境变量、token、绝对路径、私有 URL、源码或完整对话。正则不能保证自由文本安全。
不建本地事件日志或阶段文档副本，Issue 为持久事实源；远程不可用沿用 fallback。缺 CLI 或授权必须停止并交给用户安装/登录指南。

维护上游固定为 `https://github.com/askdaddy/Git-Issue-Loop-Skill.git`。
1. 在单独维护工作副本核验 `git remote get-url origin` 与该 URL 相同；脚本按 cwd remote 路由，禁止在业务仓库误开维护票。无可用维护副本时停止上游步骤，不改业务 remote。
2. 经该副本 `scripts/git-ops.sh --role <角色> issue list --state all`，按指纹核对 open 和 closed 候选，再 `issue get <N>` 阅读证据。查询不携带私有业务内容，无法完整读取时报告去重未完成，不宣称无重复。
3. 呈报确切上游、create 或 comment、完整脱敏标题/正文、候选与去重结论，等待用户授权这次写入。业务 Issue 授权不包含向维护上游披露信息。既有持续授权须能覆盖目标、内容与动作；不自动推定。
4. 获授权后仅经该副本包装器 `issue create` 或 `issue comment` 写入。同根因追加实例并关联原反馈；已修复后复发保留新实例、原版本及修复版本，不静默去重丢弃。新建立即由 PM 设置 p0～p3；遵守原角色权限，跨角色任务先切换。
5. 回读确认；部分失败报告已完成动作和未完成动作，避免盲目重试造成重复。反馈未提交必须明确说明，不标成功。

## 维护与正向验证

用评论字段 `feedback-state` 表达待归因→待处理→修复中→已发布待观察→已验证，或误报；独立于 RIPER 状态族，不新增受管标签。
维护者确认归因，记录最小复现和回归用例；修复关联 commit、发行版、适用宿主/平台及回归结果。
尚未发布则发行版 unknown，不能提前称已发布。没有后续运行证据则停在已发布待观察，不能称已验证。
更正误报保留原事件，追加更正原因与证据，不能删除历史。实例与修复互相引用。

正向结果包括成功拦截、安全恢复、反馈促成回归修复、误报纠正。
观察记录窗口、Skill 版本、环境、事件实例数、确认问题数、可检测操作机会数（分母）。
拦截率只在有明确口径的确认事件中计算；复发按规则/根因及版本比较；同时看误报率和恢复耗时。
样本不足、无分母或版本混杂记无法判断；零报告不等于零违规，不按反馈数量奖励或考核。
回归验证机制可用与真实运行改善分开汇报；禁止自动改 Skill 或放宽业务验收标准。
